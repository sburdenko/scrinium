Brightmoor Sync User Guide

Brightmoor Sync keeps folders on your own servers and buckets in the cloud in step. A small agent runs next to your data, watches for changes and moves them in both directions. This guide covers installation, configuration and the most common errors.

Installation

The agent runs on Linux, macOS and Windows Server. Before you start, make sure the machine meets these requirements:

  • Node.js 22 or later
  • At least 2 GB of free disk space for the change journal
  • Outbound HTTPS on port 443 to api.brightmoor.dev

Install the command line tool from npm:

npm install -g @brightmoor/cli@4

Then link the machine to your workspace and start the agent:

brightmoor login --workspace <workspace-id>
brightmoor agent start

The agent registers itself as a system service, so it starts again after a reboot.

Configuration

All settings live in one file, ~/.brightmoor/agent.toml. The agent reads it at start and again whenever the file changes, so you do not have to restart anything after an edit. Settings you leave out keep their defaults.

Sync schedule

The agent does not copy every change the moment it happens. It collects changes in a journal and works through them in rounds. Each round starts with a scan of the watched folders, compares what it finds with the journal, and then uploads and downloads whatever differs. Grouping work this way keeps the number of requests low and lets the agent skip files that change several times in quick succession, such as documents that an editor saves every few seconds.

How long a round takes depends on the number of files rather than their size. A folder with a few hundred large videos is scanned in seconds, while a folder with a million small log files can take several minutes. If a round is still running when the next one is due, the agent does not start a second round in parallel; it waits until the first one has finished and then starts immediately. You can see the length of the last rounds with brightmoor status.

Quiet hours let you keep the network free during the working day. Inside quiet hours the agent still scans and records changes, but it moves no data. Outside quiet hours it catches up. Quiet hours are set as a list of time ranges in the local time of the machine, and they may cross midnight.

Large first syncs are a special case. When you connect a folder that already holds many files, the first round uploads all of them and can run for hours. The agent shows its progress in brightmoor status and can be stopped and started again at any time; it continues where it left off instead of starting over, because the journal records every file that has been transferred.

Rounds are also triggered by events. When the operating system reports a change in a watched folder, the agent notes it in the journal at once, so that the next round does not have to find it by scanning. On network drives such events are not reliable, which is why the agent always scans as well, and why rounds on network drives take longer.

The time between two rounds is called the interval. If you set nothing, the agent runs every 15 minutes. The shortest interval it accepts is 5 minutes; lower values are rounded up, and the agent writes a warning to its log when it does so.

[schedule]
interval = "15m"
quiet_hours = ["08:00-18:00"]

Conflict handling

A conflict happens when the same file changed on both sides between two rounds. This is rarer than it sounds, because most teams work in either the local folder or the bucket, not both, but it does happen when a script in the cloud rewrites a file that someone is also editing on a server. The agent never asks you to choose in the moment, because it usually runs on a machine where nobody is watching.

To decide, the agent compares the modification times that both sides report. Clocks on servers and in storage services drift, so the agent allows for a tolerance of two seconds; changes closer together than that are treated as simultaneous, and then the side with the larger file is taken as the newer one. Folders are never in conflict as such: if a folder was renamed on one side and filled with new files on the other, the agent applies both changes.

Deletions are handled carefully as well. A file that was deleted on one side and changed on the other is restored, because losing a change is worse than keeping a file that someone wanted gone. The restore is recorded in the log with the path and both timestamps, so you can find out later who did what.

Some file types are never merged or compared by content. Office documents, images and archives are treated as a whole: either one version is kept or the other. Plain text files are treated the same way, even though a merge would sometimes be possible, because a merge that goes wrong is harder to notice than a conflict copy.

If you see many conflicts, look for two processes writing to the same files. A common cause is a backup tool that touches the modification time of every file it reads. Excluding the watched folder from that tool, or switching it to read-only access, usually ends the conflicts.

When both sides changed, the most recent change wins. The losing copy is not deleted: it is moved to the .brightmoor/conflicts folder next to the watched folder and kept there for 30 days before it is purged.

Bandwidth limits

Set upload_limit and download_limit in megabits per second to keep the agent from filling the line. Both are unlimited by default, and the value 0 also means unlimited.

Troubleshooting

The agent writes its log to ~/.brightmoor/logs and keeps it for 14 days. Most problems show up there as an error code:

Error codeMeaningWhat to do
E401The API key has expired or was revokedRun brightmoor login again
E429The workspace hit its rate limitNothing; the agent waits and retries
E507The destination disk is fullFree space or move the watched folder
