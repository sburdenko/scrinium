Brightmoor API Reference

The REST API lets you manage workspaces, agents and sync jobs from your own tools. All endpoints live under https://api.brightmoor.dev/v2 and exchange JSON.

Authentication

Every request carries the API key in the X-Brightmoor-Key header. Requests without a valid key are answered with status 401.

curl https://api.brightmoor.dev/v2/agents \
  -H "X-Brightmoor-Key: $BRIGHTMOOR_KEY"

Keys are created under Settings, API keys. A key expires 365 days after it was created; the workspace owners receive an email two weeks before that.

Rate limits

Limits apply per workspace, not per key, so several scripts that share a workspace also share its budget. The budget depends on the plan of the workspace.

Starter plan

Requests are counted in a sliding window of sixty seconds. Every call counts once, whatever its size: listing ten agents costs as much as listing a thousand. Calls that fail with status 401 or 404 count as well, because the work of checking them still happens on the server, so a script that keeps retrying with an expired key can use up the budget of everyone else in the workspace.

Each response tells you where you stand. The header X-RateLimit-Remaining holds the number of calls left in the current window, and X-RateLimit-Reset holds the number of seconds until the oldest call drops out of it. Well-behaved clients read both and slow down before they reach zero, instead of waiting for an error. The official SDKs do this for you.

Bursts are allowed within the window. A client may send its whole budget in the first second and then wait, or spread it evenly; both are fine. What the server does not allow is a steady stream above the budget. Long-running exports should therefore page through results at an even pace rather than in a tight loop.

When a script reaches the limit, the right reaction is to wait, not to try harder. Retrying at once only adds more rejected calls to the window and delays the moment when calls are accepted again. The SDKs wait for the time the server names and then resume where they stopped, and a hand-written client should do the same.

Limits are checked before anything else, so a rejected call has no effect: no job is created, no setting is changed and no email is sent. It is therefore always safe to repeat a call that was turned away. Calls that were accepted but timed out on your side are a different matter; repeat those with the same idempotency key so that the server can recognise the repeat.

The ceiling is 60 requests per minute. A request above the ceiling is answered with status 429 and a Retry-After header of 60 seconds. The ceiling cannot be raised; move the workspace to a larger plan if you need more.

Team plan

Counting works the same way as everywhere else: a sliding window of sixty seconds in which every call counts once. Webhook deliveries that the server sends to you do not count against the budget, and neither do the calls that the sync agent itself makes, because the agent has a budget of its own that grows with the number of connected machines.

Teams usually run several integrations in one workspace, for example a reporting job, a provisioning script and a chat bot that posts sync failures. Because they share the budget, give each of them its own key. The usage page in the dashboard then shows how many calls each key made in the last hour, which makes it easy to find the integration that runs too hot.

If an integration needs to fetch a lot of data, prefer the bulk endpoints. One call to /v2/jobs:batchGet returns up to 100 jobs and costs one request, while fetching the same jobs one by one costs a hundred. The bulk endpoints are listed with a note in this reference.

Scheduled jobs tend to start at the full hour, and when several of them do, they compete for the same window. Spread their start times by a few minutes, or add a random delay of up to a minute at the start of each run. This alone removes most of the rejected calls that teams report to support.

The dashboard keeps the history of rejected calls for 30 days. A spike usually points at one key, and the request log next to it shows which endpoint that key called. Revoking a key takes effect at once, which is the quickest way to stop a runaway script while you fix it.

The ceiling is 600 requests per minute. A request above the ceiling is answered with status 429 and a Retry-After header of 20 seconds. The ceiling cannot be raised; move the workspace to a larger plan if you need more.

Enterprise plan

Calls are counted in the same sliding window of sixty seconds. Large organisations often connect identity providers, ticket systems and their own monitoring, and many of these poll the API on a schedule. Polling is the most common reason for running into the limit, so use webhooks for events whenever you can and keep polling for reconciliation jobs that run a few times a day.

Workspaces on this plan can be split into projects, and each project can be given a share of the workspace budget. A share is a ceiling, not a reservation: unused capacity of one project is not handed to another. Shares are set by the workspace owners in the dashboard and take effect within a minute.

For migrations and other one-off jobs, the support team can lift the limit for a fixed period. Ask at least three working days before the job, name the period and the expected number of calls, and the change is confirmed in writing.

Reconciliation jobs that compare the state of thousands of agents with an inventory system should use the export endpoint instead of listing agents page by page. An export runs on the server, is delivered as a file to a bucket you name, and costs a single request no matter how large it is. Exports can be scheduled to run every night.

Audit and compliance tools that read the event log can subscribe to the event stream rather than polling. The stream keeps a connection open and pushes each event within seconds, so the tool sees changes earlier and makes almost no requests at all.

The ceiling is 3000 requests per minute. A request above the ceiling is answered with status 429 and a Retry-After header of 5 seconds. Unlike on the smaller plans, the ceiling can be raised on request.

Pagination

List endpoints return results in pages. Set page_size to choose how many items a page holds; the default is 50 and the largest page size the API accepts is 200. Each page carries a next_cursor, which you pass back as cursor to fetch the next one. The last page has no cursor.

import requests

def all_jobs(key):
    cursor = None
    while True:
        params = {"page_size": 200, "cursor": cursor}
        page = requests.get("https://api.brightmoor.dev/v2/jobs",
                            headers={"X-Brightmoor-Key": key}, params=params).json()
        yield from page["items"]
        cursor = page.get("next_cursor")
        if cursor is None:
            break

Webhooks

Webhooks tell your system about events such as a finished sync job or an agent that went offline. A delivery that does not get a 2xx answer within ten seconds counts as failed and is retried up to 5 times, with growing pauses of 1 minute, 5 minutes, 30 minutes, 2 hours and 12 hours.

To check that a delivery really came from Brightmoor, compute an HMAC-SHA256 of the raw request body with the webhook secret and compare it with the X-Brightmoor-Signature header:

import hashlib, hmac

def is_genuine(body: bytes, signature: str, secret: str) -> bool:
    expected = hmac.new(secret.encode(), body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)
